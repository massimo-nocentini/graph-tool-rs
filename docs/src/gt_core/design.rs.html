1//! # graph-tool 3.8 → Rust: the architecture of record
2//!
3//! This document is authoritative. Where it disagrees with a comment in the code,
4//! the code is wrong. Where a public signature here cannot be made to compile, the
5//! signature was changed and the change is recorded in §13.
6//!
7//! Everything asserted below about the C++ was read in
8//! `../src/graph` at the stated line. Everything asserted about the Rust was
9//! compiled with rustc 1.98.1; the layout numbers and the compiler diagnostics in
10//! §9 and §10 are copied from a run, not recalled.
11//!
12//! ---
13//!
14//! ## 0. What this port is, and what it is not
15//!
16//! graph-tool is a dynamically typed Python frontend over monomorphic C++ kernels.
17//! The C++ recovers the static type at the boundary by a linear `any_cast` scan
18//! over a Hana cartesian product of graph views × property value types, then hands
19//! the resolved types to a template. That shape is not an accident and this port
20//! does not try to remove it: **a dynamically typed frontend still needs the
21//! product.**
22//!
23//! What the port changes is the *kind of failure* available at each layer:
24//!
25//! | layer | graph-tool | here |
26//! |---|---|---|
27//! | a dispatch axis has no arm | runtime `DispatchNotFound`, message: "This is a graph_tool bug. :-(" (`dispatch.hh:86-88`) | exhaustive `match`; a new view is `error[E0004]` |
28//! | a state supplies a member under the wrong name | silently inherits a *working* default (`spec_base.hh:88-109`) | `error[E0407]` / `error[E0046]` |
29//! | a property map is shorter than the graph | unchecked write (`dispatch.hh:174` → `fast_vector_property_map.hh:218`) | the short view is not a constructible value |
30//! | an undirected view is asked for in-edges | empty range (`graph_adaptor.hh:224-233`) | `error[E0599]` |
31//! | a Python-valued map reaches a parallel loop | happens, with the GIL released (`graph_properties_copy.cc:35-42`) | `error[E0599]`: the type is `!Send` |
32//! | two derived indexes disagree | possible; `check_epos` exists and every call site is commented out (`:1206`, `:1289`, `:1433`) | `validate()` runs after every mutation under `debug_assertions` |
33//!
34//! It is **not** a performance rewrite. §12 is an honest ledger, and it contains
35//! three places where this port is slower than the C++ and says so.
36//!
37//! ---
38//!
39//! ## 1. Crate layout
40//!
41//! ```text
42//! graph-tool-rs/
43//!   Cargo.toml                     workspace, resolver 3, edition 2024
44//!   Makefile                       `make doc`: rustdoc for the workspace -> docs/
45//!   crates/
46//!     gt-core        ids · dir · adj · view · prop · par · bound · graph
47//!                    design · implementation_plan   ← this document and the plan
48//!     gt-algo        traversal · components · degree · centrality · topology
49//!     gt-inference   delta · spec · metropolis · blockmodel
50//!     gt-io          gt · graphml · dot · csv
51//!     gt-py          gil · dispatch · value · module     ← the only crate naming pyo3
52//!   docs/                          generated by `make doc`; never edited by hand
53//! ```
54//!
55//! Five crates, not the eleven the source designs proposed between them. Two
56//! reasons. First, the `value_subset!` macro and the types it names
57//! (`ValueKind`, `DispatchError`, `PropValue`) **must live in the same crate**: a
58//! `macro_rules!` body expanding `$crate::ValueKind` resolves `$crate` to the crate
59//! that *defines the macro*, so splitting them gives `error[E0433]: could not find
60//! ValueKind in crate $crate` at every invocation. Second, crate boundaries are
61//! recompilation boundaries and there are ~21 000 monomorphised leaves to get
62//! through; five is already coarse enough to hurt (§10).
63//!
64//! `gt-core` carries two optional features:
65//!
66//! * `python` — compiles `prop::value::PyValue`. gt-py enables it. The Python
67//!   member of the value universe lives in gt-core, not gt-py, because
68//!   `PropValue`'s seal is a **private** module: if the trait could be implemented
69//!   downstream, a newtype over a bare `pyo3::Py<PyAny>` could re-enter the
70//!   universe with `Send + Sync` intact and defeat §7 entirely.
71//! * `wide-index` — swaps `ids::Raw` from `u32` to `u64`.
72//!

74//!
75//! ## 2. The contested decisions
76//!
77//! Six independent designs produced four graph traits (three of them named
78//! `GraphRef`), three view mechanisms, three edge descriptors, five property-map
79//! types, four branding schemes and two index widths. Both judges concluded the
80//! set was not implementable as a merge. These are the resolutions, each with the
81//! evidence that decided it.
82//!
83//! ### D1 — The graph trait is **not** GAT-based
84//!
85//! **Decided:** `trait GraphRef: GraphBase + HasDir` with plain associated types,
86//! implemented on `&'g AdjList` and on view *values*, every method taking `self`
87//! by value.
88//!
89//! **Rejected:** `trait Incidence { type OutEdges<'a> where Self: 'a; fn out_edges(&self, v) -> Self::OutEdges<'_> }`.
90//!
91//! The GAT form fails three ways, each fatal to a different part of the port:
92//!
93//! * `&dyn Incidence` is `error[E0038]: the trait is not dyn compatible because it
94//!   contains generic associated type OutEdges`. graph-tool's whole Python
95//!   boundary is runtime dispatch over graph kinds. It cannot be built on that
96//!   trait.
97//! * `where for<'a> G::OutEdges<'a>: Send` — the bound rayon needs — is accepted
98//!   for an owned graph and rejected for any *borrowing view* with
99//!   `error[E0597]` and rustc's own note that the GAT's implicit `where Self: 'a`
100//!   "implies a `'static` lifetime". So `Und(&g)` could never reach a parallel
101//!   loop.
102//! * The usual escape, a refinement trait
103//!   `trait SizedIncidence: Incidence where for<'a> Self::OutEdges<'a>: ExactSizeIterator`,
104//!   is well-formed and unimplementable for any borrowing wrapper
105//!   (`error[E0477]`). So the filtered-view question would have *no* answer.
106//!
107//! Putting the lifetime on the implementing type costs nothing: `Self::Out` is
108//! still `OutEdges<'g>`, `fold` still forwards to `slice::Iter::fold`, and views
109//! are one machine word (verified: `size_of::<Und<&AdjList>>() == 8`).
110//!
111//! ### D2 — Incidence is **anchored**; identity is `EdgeId` and nothing else
112//!
113//! **Decided:** two descriptor types.
114//!
115//! * `Incident { other: VertexId, edge: EdgeId }`, yielded by `out_edges`,
116//!   `in_edges`, `all_edges`. `other` is **always the neighbour**.
117//! * `EdgeRef { id, src, tgt }`, yielded by `edges()` and `find_edge`, in
118//!   canonical storage orientation.
119//!
120//! Neither implements `PartialEq` or `Hash`. Verified: `a == b` on two `EdgeRef`s
121//! is `error[E0369]`, and `HashSet<EdgeRef>::insert` is `error[E0599]`. Identity
122//! goes through `.id()` or `From`.
123//!
124//! **Why anchored.** Two of the six designs got undirected traversal silently
125//! wrong, in opposite directions, and both misread the same C++. The ground truth:
126//!
127//! ```c++
128//! // graph_adaptor.hh:199-207
129//! out_edges(u, undirected_adaptor<Graph>& g) { return _all_edges_out(u, g.original_graph()); }
130//! // graph_adjacency.hh:1102-1108   — note the iterator type
131//! _all_edges_out(Vertex v, const adj_list<Vertex>& g) {
132//!     typedef typename adj_list<Vertex>::out_edge_iterator ei_t;   // OUT, not ALL
133//!     return {ei_t(v, es.begin()), ei_t(v, es.end())};             // the WHOLE block
134//! }
135//! // graph_adjacency.hh:298-306
136//! struct make_out_edge { static edge_descriptor def(vertex_t src, const pair& v, Iter&&)
137//!     { return edge_descriptor(src, v.first, v.second); } };       // src == u, always
138//! ```
139//!
140//! So graph-tool's undirected view **normalises**: `src == u` for the in-half too,
141//! and the `std::swap` at `graph_adaptor.hh:161` exists to make `edge(u,v,g)`
142//! *agree* with that. The view is self-consistent; what one design mistook for an
143//! inconsistency was `all_edges(v, g)` on a *directed* `adj_list`, a different
144//! function.
145//!
146//! A symmetric `{src, tgt, idx}` POD cannot record "stored 2→1, traversed from 1".
147//! `Incident` does not have to: the field is named `other` and there is no second
148//! interpretation. This also makes the filtering adaptors cheaper — `FilterIncident`
149//! needs only the iterator and the filter, never the graph, because the
150//! neighbour is already in hand.
151//!
152//! **Why no `Eq`.** `operator==` on `adj_edge_descriptor` compares `idx` **only**
153//! (`:196`) and `hash` is `e.idx` (`:1618`), so `unordered_set<edge_descriptor>`
154//! dedupes correctly — which undirected algorithms rely on. One design "fixed"
155//! this by deriving equality over all three fields, which silently changes results
156//! for every such set. Refusing to implement `Eq` at all makes the port of that
157//! code a compile error that points at the right line.
158//!
159//! ### D3 — Views are composed newtypes with **normalising constructors**
160//!
161//! **Decided:** `Und<G>` and `Rev<G>`, `#[repr(transparent)]`, **private fields**,
162//! reachable only through `Undirect::undirect` and `Reverse::reverse`, whose impls
163//! make `undirect` idempotent and absorbing and `reverse` an involution. Filtering
164//! is a **type parameter** `Filtered<G, F: Filter>` with a `KeepAll` ZST.
165//!
166//! **Rejected:** flattening all six into
167//! `GraphView<'g, const D: bool, const R: bool, const F: bool>`.
168//!
169//! Const-folding is real — one judge measured 27 vs 45 instructions for the
170//! unfiltered and filtered arms of the flattened form. But flattening is also
171//! exactly what throws away the orientation information that
172//! `undirected_adaptor::source/target` carries, and the design that shipped it had
173//! four of six views semantically wrong (reversed yielding base-out ∪ base-in
174//! where `graph_reverse.hh:78-80` swaps the iterator typedefs and means base-in
175//! *only*). Composed wrappers plus an anchored `Incident` keep the orientation and
176//! get the same monomorphisation, because `Und<G>::Out = G::All` is resolved at
177//! the type level exactly as a const parameter would be.
178//!
179//! Verified, by `std::any::type_name` on a real build:
180//!
181//! ```text
182//! d.reverse().reverse()   = &AdjList                  (involution)
183//! d.reverse().undirect()  = Und<&AdjList>             (absorbing, not Und<Rev<_>>)
184//! d.undirect().undirect() = Und<&AdjList>             (idempotent)
185//! Rev<Und<&AdjList>>      = error[E0271]: type mismatch resolving
186//!                           <Und<&AdjList> as HasDir>::Dir == Directed
187//! ```
188//!
189//! This is **stronger** than `graph_filtering.hh`. C++ drops the impossible corner
190//! with a `hana::filter` (`:112-118`) and de-duplicates the rest with
191//! `hana::to<set_tag>` (`:127`); the struct bound alone kills only the filtered
192//! case, and the *duplicates* — `Und<Und<_>>`, `Rev<Rev<_>>` and the tower above
193//! them — are what normalising constructors close. Private fields are what make
194//! that closure real: `Undirected<G>(pub G)` would let `u.0.in_edges(v)` compile
195//! and defeat the `Bidirectional` separation entirely.
196//!
197//! **Why a type parameter for filtering, not a const generic or a runtime
198//! predicate.** A const generic erases no *data*, so the mask fields would exist
199//! in the unfiltered arm and need dummy values; a runtime `&dyn Fn` gives one
200//! instantiation instead of six — a real compile-time win — at the cost of an
201//! unspeculatable indirect call in the inner loop. Type parameter with a ZST for
202//! "off" gives the same six as C++ with neither cost. (Corroboration: the design
203//! that chose the const-generic form shipped a `vmask` field that was **read
204//! nowhere**, so every filtered measurement it reported was of a no-op.)
205//!
206//! ### D4 — Directedness is split: `Dir` *and* `HasDir`
207//!
208//! `trait Dir { const DIRECTED: bool; const N_FIELDS: usize; }` carries the
209//! type-level directedness **and its field set** — which is what lets an
210//! undirected SBM delta buffer hold two adjacency half-field vectors instead of
211//! four, rather than four empty ones.
212//!
213//! `trait HasDir { type Dir: Dir }` is separate so that non-`Copy` **owners** can
214//! carry directedness. `Arc<AdjList>: HasDir` is what makes
215//! `Und<Arc<AdjList>>` — the safe replacement for
216//! `std::reinterpret_pointer_cast<ug_t>(u)` (`graph_filtering.cc:92`) — expressible
217//! at all. Verified: `size_of::<Und<Arc<AdjList>>>() == size_of::<Arc<AdjList>>() == 8`,
218//! the same layout the cast produces, obtained by a move.
219//!
220//! `Field<D>` replaces the `InFields for ()` trait one design used, whose `slot()`
221//! was an `unreachable!()` in safe code, unreachable only because every caller
222//! branched on `D::DIRECTED` first — an invariant stated in a comment and nowhere
223//! in a type. That is the same species of defect as the `_dummy` fallthrough it
224//! was meant to fix.
225//!
226//! ### D5 — Index width is a crate-wide **alias**, not a type parameter
227//!
228//! `pub type Raw = u32;` (`u64` under `wide-index`). `Id<T: IdTag>` is a
229//! newtype over it.
230//!
231//! The designs disagreed: one made `I: RawId` a parameter defaulted to `u32` and
232//! built its whole cache-line argument on it; one used `usize`; one used `u32`.
233//! The parameter version is worse than either fixed choice, because it multiplies
234//! every generic algorithm in the port by two for a capability nobody has asked
235//! for. Making it an alias removes an entire monomorphisation axis from every
236//! signature and still leaves `u64` reachable by a whole-build flag.
237//!
238//! The width itself: verified `size_of::<AdjEntry>() == 8`, against 16 for
239//! `adj_list<size_t>`'s `pair<vertex_t, vertex_t>` — eight entries per 64-byte
240//! line against four, on the memory stream that dominates BFS, triangle counting
241//! and SBM neighbour sweeps. Ceiling 4.29 × 10⁹ vertices.
242//!
243//! Note graph-tool already has *two* widths and asserts neither: `_epos` is
244//! `vector<pair<uint32_t,uint32_t>>` (`graph_adjacency.hh:620`) beneath a `size_t`
245//! vertex. Here positions are `Raw` too, so that cannot recur — a claim one design
246//! made in its rationale and contradicted six lines later in its own code.
247//!
248//! ### D6 — The kernel-facing property map is a **trait**
249//!
250//! `trait ReadProp<K: IdTag>` with `type Ref<'s>: Deref<Target = Self::Value>`.
251//! Implementations: `DenseProp` (owns a `Vec`), `PropSlice`/`PropSliceMut`
252//! (views), `IndexProp` (**no storage**), `Unity` (ZST), `Constant`, `ConstI64`.
253//!
254//! This is not stylistic. `vertex_index_map_t` and `edge_index_map_t` are
255//! `hana::append`ed to every non-`writable_` property axis:
256//!
257//! ```c++
258//! // graph_properties.hh:166-180
259//! inline constexpr auto vertex_properties =
260//!     hana::append(get_vprop_types(value_types), hana::type<vertex_index_map_t>());
261//! inline constexpr auto scalar_vertex_properties =
262//!     hana::append(get_vprop_types(scalar_types), hana::type<vertex_index_map_t>());
263//! ```
264//!
265//! Those axis names appear in roughly three quarters of the 324 dispatch call
266//! sites. `vertex_index_map_t` is a *storage-free identity map*: it has no vector
267//! and no slice. **All five property-map designs proposed by the source lenses
268//! model a map as an owned `Vec<T>` or an `&mut [T]`, so none of them can
269//! represent the most common argument the dispatcher passes.** Only a trait can.
270//!
271//! Reads return `Self::Ref<'s>: Deref`, not `Self::Value`. Returning by value
272//! costs a heap allocation, a `memcpy` and two deallocations per element for
273//! `String` and the seven vector members — nine of the fifteen — which is exactly
274//! the inner loop of `graph_properties_copy.hh:62`, where the C++
275//! `pm[k] = src_ref` reuses the target's capacity and allocates nothing.
276//!
277//! ### D7 — The value universe: no `Default`, no `Send`, no `Sync` on the base trait
278//!
279//! ```rust,ignore
280//! pub trait PropValue: sealed::Sealed + 'static { const KIND: ValueKind; type Elem: PropValue; }
281//! pub trait Zeroed:  PropValue { fn zero() -> Self; }      // the 14 non-Python members
282//! pub trait GilFree: PropValue + Clone + Send + Sync {}    // the 14 again, as a marker
283//! pub trait ToF64:   Copy      { fn to_f64(self) -> f64; }
284//! pub trait Scalar:  PropValue + GilFree + Copy + ToF64 + PartialOrd {}
285//! ```
286//!
287//! Two source designs wrote
288//! `PropValue: Sealed + Default + Send + Sync + 'static`. Both bounds are wrong:
289//!
290//! * **`Default`** is unimplementable for the 15th member. pyo3 has no
291//!   `impl Default for Py<T>`; the default `python::object` is `Py_None`, which
292//!   needs a live interpreter and an incref. So `data.resize_with(n, T::default)`
293//!   — the body of the central sizing chokepoint — cannot exist for it. Growth
294//!   here takes a `FnMut() -> T` closure (`sized_for_with`), which the PyO3
295//!   boundary fills by capturing its token; `sized_for` is the `Zeroed`
296//!   convenience.
297//! * **`Send + Sync`** is precisely what defeats the GIL guarantee, because rayon
298//!   checks `Send`, not a positive marker. With them on the base trait,
299//!   `store.as_mut_slice().par_iter_mut()` over a Python-valued map compiles with
300//!   no `unsafe` and no diagnostic.
301//!
302//! `long double` and `vector<long double>` are carried as `LongDouble([u8; 16])`,
303//! opaque, with **no arithmetic**. `.gt` files and `PropertyMap.value_type()`
304//! round-trip unchanged, and the `Scalar` bound excludes the type from every
305//! arithmetic kernel at compile time. Three designs called this a dead end; it is
306//! a one-variant decision, and it is what the subset-bound mechanism is for.
307//!
308//! `ToF64` rather than `Into<f64>`: there is **no** `impl From<i64> for f64` (it is
309//! lossy), and `int64_t` is graph-tool's most-used scalar property type. A design
310//! bounded on `Into<f64>` ships a "scalar" axis with `i64` silently missing.
311//!
312//! ### D8 — Layering: the default-body rule, and the sampler returns its own density
313//!
314//! > **A trait method may carry a default body only if that body is either a pure
315//! > no-op or derivable from other *required* methods of the same trait.** A
316//! > default that encodes policy is not a default; it is a required method.
317//!
318//! graph-tool's `SpecBase::Imp` (`spec_base.hh:58-130`) `= delete`s three members
319//! and defaults fourteen with *working* bodies, so a misnamed deleted member is a
320//! compile error and a misnamed defaulted one silently inherits. Confirmed live
321//! bug: `potts/spec.hh:113-117` overrides the proposal with
322//! `uniform_int_distribution<group_t> sample(0, _q-1)`, then `:124` defines
323//! `get_move_lprob`. `grep -rn get_move_lprob src/` finds that one line, called
324//! from nowhere. The loop calls `get_move_prob` (`base/mcmc.hh:123-124`), which
325//! Potts does not define, so it inherits `spec_base.hh:88-109` —
326//! `log(1. - d) - safelog_fast(B)`, the density of the *base's* sampler. The
327//! Hastings ratio does not correspond to the kernel being sampled.
328//!
329//! **A second instance, one layer up, not previously reported:**
330//! `loops/mcmc_loop.hh:60` declares `constexpr bool is_determinisitic()` —
331//! misspelled — while the loop calls `is_deterministic()` at `:121` and `:196`.
332//! The default is dead. It survives only because every concrete state happens to
333//! define the correct spelling.
334//!
335//! The rule alone would make both a compile error. This port goes further:
336//! `GroupProposal::propose` **returns `Proposal { to, log_fwd }`**, so there is no
337//! second place for the forward density to live. Requiring a `log_move_prob`
338//! method merely makes *misnaming* fatal; returning the density from the sampler
339//! means a copy-pasted density in the same `impl` block cannot silently disagree
340//! with a hand-written sampler. (One judge compiled exactly that: a correct
341//! uniform sampler plus a pasted base density, in one impl block, giving a
342//! Hastings ratio of −1.505 where the answer is 0.)
343//!
344//! Capabilities are **trait presence**: `Mergeable`, `ParallelMove`,
345//! `Checkpointed`. That deletes the duplicated `has_merge` (`spec_base.hh:50`) /
346//! `_has_merge` (`:115`, and again at `merge_split.hh:99`, `multilevel.hh:114`) —
347//! two independent booleans for one capability, at two scopes, which a derived
348//! spec can set inconsistently.
349//!
350//! `MoveScore { d_entropy, log_hastings }` replaces `std::tuple<double,double>`
351//! destructured positionally at `mcmc_loop.hh:174`. `Step { mv, nsteps }` replaces
352//! the `constexpr` return-type probe at `:112-118` — without it, merge-split
353//! (`merge_split.hh:1201-1203` returns `tuple<size_t,size_t>`), multiflip and
354//! multilevel cannot implement the trait at all.
355//!
356//! ### D9 — Concurrency: a scratch type, row locks, and a builder
357//!
358//! Three source designs independently removed graph-tool's concurrent mutation and
359//! **each scored the removal as a win**. It is a removed capability:
360//! `blockmodel/state.hh:152` builds `_group_mutex`, `:343-348` takes ordered pair
361//! row locks, `:451` sizes `_m_entries_pool` to `get_num_threads()`.
362//!
363//! Resolution, in three parts:
364//!
365//! 1. **`SpecCore::Scratch`.** `virtual_move(&self, ...)` cannot be implemented as
366//!    written: `blockmodel/state.hh:304` is
367//!    `get_move_entries(v, r, nr, _m_entries); move_vertex(v, r, nr, _m_entries);`
368//!    — `virtual_move` **mutates** a reusable scratch `EntrySet`, and every one of
369//!    those C++ members is non-const. `&self` plus the `Sync` supertrait leaves
370//!    only three options, all bad: allocate per Metropolis step (on the hottest
371//!    path in the library); use a `thread_local` (reintroducing exactly the
372//!    thread-keyed hidden global that `parallel_rng.hh:56-73` is condemned for,
373//!    and destroying reproducibility); or take `&mut self` (deleting the lock-free
374//!    proposal phase the whole four-phase argument rests on). Threading
375//!    `&mut Self::Scratch` is the fourth, and it makes
376//!    `_m_entries_pool.resize(get_num_threads())` an explicit per-chunk value.
377//! 2. **`BlockCommitShared` + `GroupLocks`.** Shared `&self`, `Box<[Mutex<_>]>`
378//!    taken in `(min, max)` order. What Rust adds is not a prohibition but the
379//!    enforcement `partition.hh:78-84` lacks, where `_count[r] += w` sits between
380//!    two `#pragma omp atomic` statements and is correct only if every caller
381//!    holds `_group_mutex[r]`.
382//! 3. **`ParBuilder`** for bulk construction, replacing `set_concurrent(true)`
383//!    (`graph_adjacency.hh:451`) + per-thread `_free_idx_m` (`:613`). Edge ids are
384//!    assigned by a deterministic merge in chunk order, so they do not depend on
385//!    the thread count — which graph-tool's per-thread free lists explicitly do.
386//!
387//! An "owner-computes" scheme with no locks was proposed and is **provably wrong
388//! for the block graph**: `entries.hh:391-398` writes `_mrs[me]`, `_mrp[r]` *and*
389//! `_mrm[s]` from one delta, so no partition by group makes every counter
390//! single-owner.
391//!
392//! `pair_mut` returns `Option<Pair<'_, T>>` with `Two(&mut, &mut)` **in caller
393//! order** and `Same(&mut)`. A version returning `[&mut T; 2]` sorted by index
394//! silently transposes — `pair_mut(xs, 3, 1)` hands back `[&mut xs[1], &mut xs[3]]`
395//! — which is the same class of defect `MoveScore`'s named fields exist to
396//! prevent, and graph-tool does *not* have it (`do_ulock_pair` sorts only for
397//! `std::lock`, and the caller keeps `r` and `s` by name). `Same` exists because
398//! `r == s` is the block-graph self-loop `_mrs[r][r]`, not an error case.
399//!
400//! ### D10 — The SBM lifecycle: the *level* is the unit of consumption
401//!
402//! ```text
403//! Recording<'w>  --seal()-->  Transition<'w>  --into_levels()-->  Applied<'w> (per level)
404//!                                 |                                     |
405//!                                 +-- level(l) -> Delta<'a> (Copy)       +-- commit -> Receipt
406//! ```
407//!
408//! `Transition` and `Applied` are `!Clone`; `commit` takes `Applied` **by value**,
409//! so replaying a level twice is a move error where `apply_delta`
410//! (`entries.hh:429`) has no such notion and double-counts every entry if
411//! re-entered.
412//!
413//! **Why per level and not per transition.** Taking the whole `Transition` by value
414//! makes two things impossible that the design claims to support. The always-on
415//! audit cannot be called (after `commit` the value has moved, `error[E0382]`; and
416//! before `commit` the audit fails by construction on every non-zero delta). And
417//! the **nested block model cannot be committed at all**: `apply_delta` must
418//! recurse into the coupled state with `*m_entries._next` (`:488`) — level *l*
419//! goes to state *l* — and there is only one value to give away. `Receipt` carries
420//! the before-image past the commit so the audit compiles.
421//!
422//! `Stamp { state: StateId, epoch: Epoch }`, not a bare epoch. A revision counter
423//! does not identify a state: two freshly built states both sit at epoch 0, so a
424//! transition recorded against one commits silently into the other and the guard
425//! never fires. One extra `u64` comparison per commit.
426//!
427//! **The ownership inversion is what dissolves the borrow conflict**, and the
428//! before-image is *not*. Three readers are three shared borrows and never
429//! conflicted with each other; the conflict is that the buffer is a member of the
430//! state (`state.hh:2545`), so `this->entries_dS(..., this->_m_entries)` has
431//! `&mut self` aliasing `&mut self._m_entries`. Moving the buffer into a
432//! caller-owned `Workspace` removes it, full stop.
433//!
434//! The before-image is kept for a different and honest reason: it removes two
435//! cache-cold dependent loads per entry from the pricing loop — the `_emat` hash
436//! probe and the `_mrs[me]` indirection at `state.hh:1225` — turning `entries_dS`
437//! into a contiguous scan over `&[Entry<W>]`. That is the best single performance
438//! idea in this port, and a judge verified it prices 269/269 random moves exactly
439//! against a from-scratch entropy. It is also **sufficient only for the sparse
440//! model**: the dense branch (`state.hh:1145-1219`) sweeps `out_edges_range(t, _bg)`
441//! and genuinely needs the state. Both signatures exist and say which is which.
442//!
443//! ### D11 — No branded-index `unsafe`. At all.
444//!
445//! Three designs proposed a generative-lifetime branding layer
446//! (`scope(|Domain<'id>| ...)`, `BEdgeId<'id>`, `get_unchecked`) to elide bounds
447//! checks. It is dropped. Three reasons, in order of weight:
448//!
449//! 1. **The one that shipped was unsound.** Its `brand_edge` was a *safe* function
450//!    taking a provenance-free `Copy` descriptor from any graph, bound-checked
451//!    only under `debug_assert!`, feeding `get_unchecked`. A judge got a SIGSEGV
452//!    out of it from safe code in a release build.
453//! 2. **It does not pay on the shape that matters.** Measured: on a contiguous
454//!    scan the branded form saves one `cmp`/`jae` per element (17 → 10
455//!    instructions) with no unrolling and no vectorisation — low single digits,
456//!    not the claimed 2–4×. On the *re-entry* shape that actually dominates graph
457//!    kernels (`_b[source(e, g)]`, an index read out of one map and used in
458//!    another) it was measured at **26 instructions against 17** for plain safe
459//!    indexing: a net pessimisation.
460//! 3. **The zero-unsafe path recovers most of it anyway.** `DenseProp::as_slice`
461//!    and `PropSliceMut::as_mut_slice` hand out `&[T]` / `&mut [T]`, and an
462//!    iterator over a slice carries its own length, so LLVM removes the check that
463//!    indexing cannot. No `unsafe`, no brand, no viral `'id` in every signature,
464//!    no `#[pyclass]` problem.
465//!
466//! Cross-graph confusion is caught instead by a **runtime `GraphId` comparison at
467//! kernel entry** — one compare per kernel, not per access. `Bound<K>` and
468//! `DenseProp<T, K>` both carry a `GraphId`, and `sized_for` returns
469//! `Err(PropError::WrongGraph)`. That is cheaper than a brand, catches the case
470//! the brand was *actually* needed for (`copy_property`), and costs no ergonomics.
471//!
472//! ### D12 — `remove_edge` takes an `EdgeId`, and the slot table is unconditional
473//!
474//! `EdgeSlot { src, tgt, out_pos, in_pos }` — 16 bytes, verified — so
475//! `endpoints(e)` and `remove_edge(e)` are O(1) and there is **no caller-supplied
476//! orientation left to be wrong**.
477//!
478//! This answers, affirmatively, the open question one design left: should the
479//! non-slot configuration ship? No. graph-tool makes `_epos` a runtime flag
480//! (`_keep_epos`, `:617`) and then writes `clear_vertex` **twice**, once per
481//! setting (`:1343-1414` and `:1416-1434`) — and only one of the two is wrong.
482//! With one configuration there is one algorithm.
483//!
484//! It also retires the `reverse_edge`/`remove_edge` interaction entirely rather
485//! than guarding it. A design that kept a positions-only slot table and accepted a
486//! descriptor had `remove_edge(e.reversed())` — using its own advertised
487//! replacement for `graph_adjacency.hh:571` — panic via `out_len - 1` wrapping to
488//! `usize::MAX`, with its two configurations disagreeing about whether the input
489//! was even valid.

493//! ## 3. Storage
494//!
495//! `AdjList<H: Lookup = NoLookup>`: `Vec<Block>`, `EdgeIds`, `EdgeSlots`, the
496//! lookup, a `GraphId`, and a reusable `Vec<EdgeId>` scratch.
497//!
498//! **`Block` is 32 bytes** (verified), matching graph-tool's
499//! `pair<size_t, vector<pair<size_t,size_t>>>` vertex record exactly, with no
500//! malloc for an isolated vertex (`Vec::new()` does not allocate). An inline
501//! small-vector buffer was measured at **48 bytes** — a 50% larger vertex array,
502//! streamed by every `for v in vertices { for e in out_edges(v) }` kernel — and
503//! was rejected: it helps low-degree vertices, which are not the ones carrying the
504//! edge traffic.
505//!
506//! `add_edge` is **O(1)**, by the trick at `graph_adjacency.hh:1192-1215`:
507//!
508//! ```c++
509//! if (s_pos < s_es.size()) {           // in-list is not empty
510//!     s_es.push_back(s_es[s_pos]);     // push the first in-edge to the back
511//!     s_es[s_pos] = {t, idx};          // overwrite its slot
512//! }
513//! ```
514//!
515//! One source design transliterated the surrounding code and replaced this with
516//! `es.insert(split, e)`, which is O(in-degree). A judge measured it quadratic:
517//! 20.8 / 51.6 / 207.6 / 876.3 ms for 10k / 20k / 40k / 80k insertions on a hub.
518//! On the high-in-degree hubs this library exists to analyse, that is the
519//! difference between a port and a regression.
520//!
521//! Mutation is exactly two private primitives, `splice_in` and `splice_out`, and
522//! every relocation is reported as a `Moved` **value** — so the `&mut Block`
523//! borrow ends before the index hooks run, which is what forces the correct
524//! ordering in `splice_out` and what graph-tool has to remember by hand
525//! (`:1243-1249` binds `s_es` and `t_es` as two references that alias whenever
526//! `s == t`).
527//!
528//! `num_edges()` is `EdgeIds::live()`, derived, never accumulated by caller
529//! arithmetic. `clear_vertex_where` is one loop over `remove_edge`, filling the
530//! reusable scratch — no per-call `Vec`, which a judge measured at 2–4 allocations
531//! per call in the design that used one.
532//!

535//! ## 4. Views
536//!
537//! Six types, closed by construction (D3). `Filtered::new` memoises both honest
538//! counts from `EdgeList::edges` and `VertexList::vertices` using the **same**
539//! predicate the iterators use, so `num_edges() == edges().count()` holds.
540//!
541//! Degree-summation cannot define `num_edges` on an undirected view: it
542//! double-counts, and mixing an out-edge predicate with an edge predicate makes
543//! the count and the iteration disagree. (One design reported 3 where the answer
544//! was 1, and 2 vs 4 even with the trivial filter.) That is why `EdgeList` is a
545//! bound on `Filtered::new` and why `edges()` is on the trait at all.
546//!
547//! `Filtered::masked` validates the masks against **this graph's own bounds**, so
548//! validation and use are one statement. A free-standing
549//! `MaskFilter::new(vmask, emask, vb, eb)` is `Copy` and remembers nothing: a mask
550//! admitted for a 3-vertex graph is silently accepted by a 10-vertex one and
551//! panics on first probe — the same structural defect as
552//! `graph_filtering.cc:42-46` reserving separately from `MaskFilter::operator()`.
553//!
554//! `ExactIncidence` is the refinement unfiltered views implement and filtered ones
555//! do not. `GraphRef` itself does **not** require `ExactSizeIterator`: that bound
556//! excludes filtered graphs (`error[E0277]`) and, under a GAT trait, cannot even
557//! be added as a refinement (`error[E0477]`). This is the resolution of the one
558//! question a design explicitly left open.
559//!
560//! There is no `&G → &Und<G>` reference conversion. The `ref-cast` route was
561//! dropped: it needs a dependency, and the value it produces is not a graph unless
562//! `GraphRef` is also implemented for `&Und<AdjList>` — which the design that
563//! proposed it never did, so its only use of its only dependency produced an inert
564//! value. `Und<Arc<AdjList>>` by move covers the `reinterpret_pointer_cast` case
565//! at the same layout.

569//! ## 5. Property maps and the value universe
570//!
571//! `DenseProp::sized_for(bound) -> Result<PropSliceMut, PropError>` is the single
572//! chokepoint. Growth and view-creation are one operation, so an under-sized view
573//! is not a value that exists.
574//!
575//! What it replaces:
576//!
577//! ```c++
578//! // dispatch.hh:171-177      — note: no size argument
579//! static auto& pmap(boost::checked_vector_property_map<Type,IndexMap>& a)
580//! { if constexpr (dargs.uncheck) return a.get_unchecked(); else return a; }
581//! // fast_vector_property_map.hh:108
582//! unchecked_t& get_unchecked(size_t size = 0) { reserve(size); return reinterpret_cast<unchecked_t&>(*this); }
583//! // :77    reserve only grows, so reserve(0) is a no-op
584//! // :218   unchecked operator[] has no bounds check
585//! ```
586//!
587//! So every kernel behind `gt_dispatch` receives a raw indexed map whose length was
588//! never checked against the graph, and the only guarantee is nine lines of Python
589//! (`__init__.py:363-373`). That guarantee is already violated: `graph_copy.cc:66-73`
590//! reserves `num_vertices(src)` — the *filtered* count on a filtered view — and then
591//! writes at `index_map[v]`, *unfiltered* indices built at `:222`, while the Python
592//! guard at `__init__.py:3200` also compares filtered counts.
593//!
594//! `view()` (shared) is fallible because `&self` cannot grow. Note the consequence,
595//! which one judge caught and is worth stating: graph-tool's checked map
596//! auto-grows on read (`:129`), so `g.vp.x[v]` on a never-written map returns the
597//! default. To preserve that, **the dispatcher calls `sized_for` on read-only maps
598//! too**. The two-phase reserve-then-hand-out does not disappear; it moves from
599//! Python into one place in Rust (`gt-py::module`), where forgetting it is
600//! impossible rather than merely unlikely.
601//!
602//! One consequence of that, found while wiring the boundary up and recorded here
603//! because it constrains every future entry point: sizing *cannot* be pushed down
604//! into the kernel. `DenseProp::sized_for` needs `T: Zeroed`, and none of the
605//! `value_subset!` axis traits — `Scalar`, `GilFree`, `PropValue` — implies it,
606//! precisely because `Zeroed` is the property the Python member lacks. So a kernel
607//! generic over its axis has no way to size its own map, and the sizing has to
608//! happen at the dispatched entry point while the concrete member is still in
609//! hand. An entry point that skips it hands its kernel
610//! `PropError::Undersized` on exactly the case this paragraph exists to
611//! preserve — a never-written map.
612//!
613//! `Unity` is a true ZST (verified: 0 bytes, against 1 for the C++ empty class)
614//! and implements `ReadProp` **only**. `put(UnityPropertyMap, k, v) {}`
615//! (`graph_properties.hh:714`) is a silent no-op satisfying
616//! `writable_property_map_tag` at any of the 74 call sites; here the same call is
617//! `error[E0599]` (verified).
618//!
619//! `Constant`'s field is `c` and it is **public** — which is what
620//! `graph_selectors.hh:109` and `:178` try to read on a class whose member is the
621//! private `_c` (`graph_properties.hh:677`). Both of those C++ overloads are
622//! uninstantiable dead code: graph-tool's constant-weight fast path silently does
623//! not exist.
624//!
625//! Conversion uses a crate-local `ConvertFrom`, never `From`. `impl From<Vec<i32>> for Vec<i64>`
626//! and `impl From<f64> for i32` are both `error[E0117]` from *any* crate, and
627//! `value_convert.hh:135` handles vector-to-vector while `prop_map_as` narrows, so
628//! those are the common cases.

632//! ## 6. Dispatch
633//!
634//! `value_subset!` generates, **from one token list**: the member enum, the
635//! accepted-kind array, `narrow`, the kernel trait *with its bound*, and the
636//! exhaustive match that also performs the downcast. Two consequences, both
637//! verified:
638//!
639//! ```text
640//! // a member the kernel's bound cannot handle
641//! value_subset!(pub Bad2, Bad2Kernel, "value", Scalar, { Str => String });
642//!   → error[E0277]: the trait bound `String: Scalar` is not satisfied
643//!
644//! // a transposed row
645//! value_subset!(pub Bad, BadKernel, "value", Scalar, { I16 => i32, I32 => i16 });
646//!   → error[E0080]: evaluation panicked: value_subset! Bad: variant I16 is
647//!                   mapped to i32, whose KIND differs
648//! ```
649//!
650//! The second matters more than it looks. Without the const assertion, `$v => $t`
651//! is an unchecked claim: transposing two rows compiles cleanly and produces a
652//! *runtime* `DispatchError` naming the **wrong** type as offered and listing it as
653//! accepted — strictly worse than `DispatchNotFound`, which at least prints
654//! honestly.
655//!
656//! Because the downcast happens inside the generated match,
657//! **`narrow` is the only fallible step** and kernel bodies carry no second
658//! `Result`. Otherwise every one of the ~324 call sites reintroduces
659//! `DispatchNotFound` in its own body.
660//!
661//! `AnyGraph::dispatch` is an exhaustive match over six `ViewKind`s with no
662//! catch-all: a seventh is `error[E0004]`.
663//!
664//! `DynGraph` is the dyn-compatible face for the Python boundary — internal
665//! iteration, one indirect call per **vertex** rather than per edge. A GAT-based
666//! incidence trait makes this impossible outright (`error[E0038]`), which is the
667//! single strongest argument for D1.
668//!

671//! ## 7. The Python boundary and the GIL
672//!
673//! The C++ defect, confirmed in all five copies
674//! (`graph_properties_copy.cc:35-42, :69-76, :104-111, :145-152`;
675//! `graph_properties_copy.hh:36-40`):
676//!
677//! ```c++
678//! bool is_python = (get_underlying_value_type(tgt) != typeid(boost::python::object) ||
679//!                   get_underlying_value_type(src) != typeid(boost::python::object));
680//! GILRelease gil(!is_python);
681//! bool parallel = (num_vertices(g) > get_openmp_min_thresh() && !is_python);
682//! ```
683//!
684//! The connective is wrong and the sense is inverted. `object → object` gives
685//! `is_python == false`, so the GIL is **released** *and* the loop **is**
686//! parallelised: `Py_INCREF`/`Py_DECREF` across OpenMP threads with no GIL, in
687//! exactly the case that needs it most. And `int → int` gives the opposite
688//! pessimisation: the GIL held across a long serial loop.
689//!
690//! Why the author re-derived it by hand at all is structural:
691//! `gt_dispatch_args::gil_release` (`dispatch.hh:152`) is a single compile-time
692//! constant per call site, while the value type is chosen by a *runtime* `typeid`
693//! probe. One flag cannot say "release iff this leaf has no `python::object`".
694//!
695//! Three mechanisms replace it, and it is worth being precise about which one
696//! carries the weight:
697//!
698//! 1. **Nobody writes the predicate.** `copy_prop`'s where-clause derives it as
699//!    `<S::Mode as Meet<T::Mode>>::Out`, resolved per monomorphised leaf.
700//! 2. **A wrongly edited lattice still fails.** `Par`'s bounds (`S: Sync`,
701//!    `T: Send`) are unsatisfiable for the Python member.
702//! 3. **`PyValue` is `!Send` by construction** — `PhantomData<*mut ()>`. *This is
703//!    the load-bearing one.* A positive marker trait guards only the functions
704//!    that remember to require it, and `pyo3::Py<T>` is unconditionally
705//!    `Send + Sync` (`pyo3-0.22.6/src/instance.rs:943-944`), with `Clone` and
706//!    `Drop` both doing refcount work without a token. Verified:
707//!    `Vec<PyValue>::par_iter_mut()` is
708//!    `error[E0599]: ... trait bounds were not satisfied`.
709//!
710//! And the seal is what keeps (3) from being bypassed by a sibling newtype:
711//! `PropValue`'s `sealed::Sealed` is private to gt-core, and `PyValue` lives in
712//! gt-core, so `struct RawPy(Py<PyAny>)` in gt-py **cannot be a property value at
713//! all**. (One design had exactly that hole: `impl PropValue for RawPy { type Mode = Par; }`
714//! compiled and ran `Py_INCREF` in rayon.)
715//!
716//! Also fixed, and the half a mode-lattice alone leaves open: `CopyStrategy::copy`
717//! takes the `Python<'_>` token **as a parameter of the trait method**, so `Par`
718//! cannot be implemented without `allow_threads` and `Seq` cannot run without the
719//! token held. That closes the `int → int` row.
720//!
721//! **What is *not* claimed.** `Python::with_gil` inside a rayon closure compiles —
722//! the token is acquired per worker and never crosses a thread boundary. The
723//! guarantee is that the **race** is inexpressible, not that the parallel loop is;
724//! and the price is that a Python-valued map is serialised, which is the correct
725//! behaviour and what the C++ intended before the predicate was inverted.
726//!

778//! ## 10. Instantiation budget
779//!
780//! Methodology for the C++ figures: a census over all **324** `run_action` /
781//! `gt_dispatch` call sites in `src/` (paren-balanced argument extraction,
782//! `hana::concat` treated as a sum, `hana::append` as +1, the implicit 6-view axis
783//! added for `run_action` sites naming no view range) gives **22 233 direct leaf
784//! instantiations**, median 12 per site. Largest: `graph_properties_map_values*.cc`
785//! at 1 440 each, `graph_properties_copy_imp1.cc` at 1 080,
786//! `prop_map_as` (`graph_properties.cc:69`) at 30 × 30 = 900. The commonly quoted
787//! ~35 440 additionally counts the inference module's *second* dispatch layer
788//! (`GEN_DISPATCH`, `graph_state.hh:384-410`). 275 `.cc` files exist under `src/`.
789//!
790//! | axis | graph-tool | here | note |
791//! |---|---:|---:|---|
792//! | graph views | 6 | 6 | parity; both exclude undirected∧reversed |
793//! | full value universe | 15 | 15 | parity |
794//! | scalar subset | 6 | 5 | `long double` is storage-only (D7) |
795//! | integer subset | 4 | 4 | parity |
796//! | vertex-prop axis (values + index map) | 16 | 16 | `IndexProp` is the 16th |
797//! | index width | 1 (`size_t`) | **1** | would be 2 if `I` were a parameter (D5) |
798//! | slot table | 1 emitted, 2 code paths | **1** | `Epos` always on (D12) |
799//! | `(s,t)` lookup | 1 emitted, runtime flag | **1** default | `EHash` arms emitted only for actions that declare edge lookup |
800//! | conversion lattice (`prop_map_as`) | **900** | **45** | 15 identity + 15 `to_any` + 15 `from_any` (D6, §5) |
801//! | dependent axes (`last_type_func_t`, 7 families) | 1 recursion level + leaf each | **0** | `<V as PropValue>::Elem` is a projection, not an axis |
802//!
803//! **Estimated direct leaves here: ≈ 21 000.** That is 22 233 − ~855 (conversion
804//! lattice) − ~400 (dependent-axis families in the group/ungroup/copy code), i.e.
805//! **parity within 5%, not a win.** Anyone claiming a large monomorphisation
806//! saving from Rust here is mistaken; the product is a property of the problem.
807//!
808//! Where Rust is genuinely worse: graph-tool splits instantiations across 277
809//! translation units and can use `extern template`. Rust has neither —
810//! `-Z share-generics` is nightly-only. Five crates is far coarser parallelism
811//! than 277 TUs. Mitigations actually applied:
812//!
813//! * `codegen-units = 256` and `opt-level = 1` in `[profile.dev]`; ~21 000 leaves
814//!   means parallelism matters more than per-unit quality in a debug build.
815//! * `[profile.release] codegen-units = 1, lto = "fat"` — the opposite trade, and
816//!   correct there because the hot paths cross crate boundaries by construction
817//!   (gt-algo kernels generic over gt-core's `GraphRef`, gt-inference pricing over
818//!   gt-core's `ReadProp`). Without cross-crate inlining every `Incident`
819//!   manufacture and every `IS_UNITY` const-fold is lost at the crate edge.
820//! * `panic = "abort"` in release: no kernel in gt-core/gt-algo/gt-inference is
821//!   exception-safe by design (nor are their C++ equivalents), and unwind tables
822//!   across 21 000 leaves are pure size. The PyO3 boundary converts `Result` into
823//!   `PyErr`; it never relies on `catch_unwind`.
824//! * `[profile.dev] overflow-checks = true` — this catches the `_n_edges -= 2`
825//!   class directly.
826//!
827//! Where Rust is genuinely better on build time: there is no preprocessor.
828//! graph-tool parses ~4.8M lines per build (48.5× amplification across those 277
829//! TUs); `gt-core` is parsed once. The net is a front-end win and a back-end loss,
830//! and it should be *measured* on one fat module before the crate split is
831//! considered final.
832//!
833//! **Not designed yet:** the inference module's second dispatch layer
834//! (`GEN_DISPATCH` + `all_types_func_wrap`, `graph_state.hh:203-256`), which
835//! indexes resolved types **by parameter name** rather than positionally. The
836//! positional `last_type_func_t` case is solved by `PropValue::Elem`; the
837//! name-indexed case needs a generated struct of associated types and is roughly
838//! 13 000 of the ~35 000 figure. This is an open item, not a solved one.

865//! ## 12. Performance ledger, honestly
866//!
867//! ### Wins, measured or structural
868//!
869//! Numbers in this section were taken on one machine and are labelled with what
870//! was measured and how, because a ledger entry without a method is a memory.
871//! Unless another profile is named, "measured" means `[profile.bench]` (which
872//! inherits `release`: `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`) on an
873//! Intel Xeon Gold 6238R (2.20 GHz, 1 MiB L2/core, 38.5 MiB L3/socket), one
874//! thread pinned with `taskset`, criterion at 20–30 samples, rustc 1.98.1,
875//! baseline `x86-64` (no `target-cpu=native`: every packed add below is SSE2
876//! `addpd`, two lanes, not AVX's four). The box carried a load average of ~33 of
877//! 112 cores. Every number below is therefore single-threaded; `det_reduce`,
878//! `pagerank` and `ParBuilder` have benches but **no numbers are recorded for
879//! them here**, because a rayon result taken on a box with 33 cores already busy
880//! measures the box. That remains the standing open item it has been since the
881//! builder's throughput ladder was first attempted.
882//!
883//! To re-take any of it:
884//!
885//! ```text
886//! cargo bench -p gt-core      --bench adjacency   # entry_width, add_edge/scaling
887//! cargo bench -p gt-core      --bench reduce      # chunked_sum/lanes
888//! cargo bench -p gt-algo      --bench weights     # Unity / Constant / DenseProp
889//! cargo bench -p gt-algo      --bench kernels     # bfs, components, shortest_distances
890//! cargo bench -p gt-inference --bench sbm         # record, sparse_ds, move_vertex
891//! cargo test  -p gt-core      --test ledger_layout -- --nocapture   # section 11
892//! cargo test  -p gt-inference --test ledger_sbm                     # allocation counts
893//! objdump -d --disassemble=gtprobe_<name> target/release/deps/<bench>-*
894//! ```
895//!
896//! The `gtprobe_*` symbols are `#[inline(never)] #[unsafe(no_mangle)]` wrappers
897//! that exist only so that `objdump` has something to name; they live in the
898//! bench files beside the group they justify.
899//!
900//! * **2× on the adjacency stream, as a footprint. 1.22× as a time.**
901//!   `AdjEntry` is 8 bytes against graph-tool's 16 -- `graph.hh:137` fixes
902//!   `vertex_t = size_t`, so `edge_list_t` (`graph_adjacency.hh:224`) has a
903//!   16-byte element -- and `tests/ledger_layout.rs` re-derives that ratio from
904//!   `size_of::<usize>()` on every run rather than restating the 2.
905//!
906//!   The *time* ratio was not measured until now, and it is not 2. `benches/
907//!   adjacency.rs::entry_width` scans two `Vec<Vec<_>>` mirrors of the same
908//!   graph, same degree distribution, same loop, differing only in whether an
909//!   entry is `(u32,u32)` or `(u64,u64)`:
910//!
911//!   | working set | 8 B | 16 B | ratio |
912//!   |---|---:|---:|---:|
913//!   | 0.8 M entries (6.4 / 12.8 MB, in L3) | 884.8 µs | 1.083 ms | **1.22×** |
914//!   | 16 M entries (128 / 256 MB, out of L3) | 57.67 ms | 70.43 ms | **1.22×** |
915//!   | 16 M entries, one flat run, no per-vertex block | 13.85 ms | 26.19 ms | **1.89×** |
916//!
917//!   The flat row is the ceiling and it reaches the claimed 2×. The blocked rows
918//!   do not, at either working set, because a per-vertex allocation is a pointer
919//!   chase per vertex and neither width comes near memory bandwidth there (2.22
920//!   and 3.63 GB/s, against 9.24 and 9.78 GB/s on the flat run). **The entry width
921//!   is worth 1.22× on the adjacency as it is actually laid out**; the remaining
922//!   0.6× is available only to a CSR-flattened adjacency, which this port does
923//!   not have. Corrected from "2× on the adjacency stream", which quoted the
924//!   footprint ratio as though it were the throughput ratio.
925//!
926//! * **The before-image.** Two cache-cold dependent loads per entry removed from
927//!   `entries_dS`, the hottest kernel in the library (D10). Confirmed at the
928//!   instruction level rather than argued: `state.hh:1226-1231` does
929//!   `_emat.get_me(t, w)` and then `_mrs[me]`, two dependent loads per entry,
930//!   while `objdump --disassemble=gtprobe_sparse_ds` on `benches/sbm.rs` shows
931//!   the port's loop reading `0x8(%r12,%rbx,1)` and `0x10(%r12,%rbx,1)` --
932//!   `mrs_before` and `delta`, both out of the entry itself -- and advancing with
933//!   `add $0x20,%rbx`, one contiguous 32-byte stride. The price paid for it is
934//!   the entry width: `Entry<W>` is 32 bytes because it interns `me` and
935//!   `mrs_before`.
936//!
937//!   Measured (`benches/sbm.rs::sbm/sparse_ds`, deltas of 4/17/24/32 entries,
938//!   66.98 / 180.55 / 240.44 / 310.42 ns): a least-squares fit is **8.69 ns per
939//!   entry plus 32.4 ns fixed** -- the fixed part being the two `vterm` pairs at
940//!   `r` and `nr` -- and all four points sit within 0.3% of that line. A shape
941//!   that re-derived `mrs` per entry could not be linear in the entry count at a
942//!   flat per-entry cost.
943//!
944//! * **`Block` at 32 bytes with no per-vertex malloc** for isolated vertices --
945//!   **which is parity with graph-tool, not a win over it.** Its vertex record
946//!   (`graph_adjacency.hh:225`, `pair<size_t, edge_list_t>`) is 8 + 24 = 32 too,
947//!   and `add_vertex` (`:1318-1336`) `emplace_back`s a default-constructed
948//!   `vector`, which does not allocate either. Both halves are parity. Listed
949//!   here because it is a property worth *keeping* -- an inline small-vector
950//!   buffer was measured at 48 bytes and rejected -- not because it is an
951//!   advantage. `tests/ledger_layout.rs::block_is_one_vec_plus_one_word_and_an_empty_one_does_not_allocate`
952//!   pins it.
953//! * **Monomorphised `Dir` / `Filter` / `Lookup`** delete the runtime flag tests
954//!   C++ performs inside `add_edge` (`:1195`, `:1213`), `remove_edge` (`:1251`)
955//!   and `reverse_edge` (`:576`). Visible in the `entries_dS` disassembly above:
956//!   `eterm::<D>` branches on `D::DIRECTED || r != s`, so at the `Directed`
957//!   instantiation the `r` and `s` fields of `Entry` are **never loaded at all**
958//!   -- the 694-instruction body of `sparse_terms::<Directed, i64>` touches only
959//!   offsets `0x8` and `0x10` of each 32-byte entry.
960//!
961//! * **The `Unity` weight map costs nothing, measured three ways.**
962//!   `weighted_out_degree` (`gt-algo/src/degree.rs:122-136`) selects one of three
963//!   arms on `W::IS_UNITY` / `W::IS_CONSTANT`, and section 11's `Unity` row (0
964//!   bytes) is only half the claim. `benches/weights.rs` carries three
965//!   `#[inline(never)]` probes at the three monomorphisations, so
966//!   `objdump --disassemble=gtprobe_*_out_degree` settles it in the shipped
967//!   profile rather than in a test binary:
968//!
969//!   | arm | instructions | backward branch | loads from the map |
970//!   |---|---:|---|---|
971//!   | `Unity` | **14** (10 on the empty-block path) | none | **none, at any address** |
972//!   | `Constant` | 34 | none | one `mulsd (%rdx)`, hoisted out of nothing |
973//!   | `DenseProp<f64>` | 29, of which a **7-instruction loop** | yes | one `addsd (%rcx,%rdi,8)` per incident edge |
974//!
975//!   "Folds to a couple of instructions" was the standing informal claim; 14 is
976//!   the measured number. Static size is the wrong axis anyway -- `Constant` is
977//!   the *largest* of the three and the second cheapest -- so what the table is
978//!   for is the other two columns: whether there is a loop over the
979//!   neighbourhood, and whether the map is read at all. Wall clock, 100 000
980//!   vertices / 500 000 edges:
981//!
982//!   | sweep | `Unity` | `DenseProp<f64>` | ratio |
983//!   |---|---:|---:|---:|
984//!   | `sum_v weighted_out_degree` (500 k incidences) | 130.4 µs | 2.242 ms | **17.2×** |
985//!   | `sum_v weighted_degree` (1 M incidences) | 125.2 µs | 4.424 ms | **35.3×** |
986//!
987//!   The unity arm does not scale with the edge count because it does not read
988//!   edges: both rows are ~1.3 ns per *vertex*. `Constant` is 147.5 µs, i.e.
989//!   1.13× the unity arm and 15× cheaper than the general one, which is the
990//!   `IS_CONSTANT` arm earning its place. The `DenseProp` inner loop retains its
991//!   bounds check and a reachable `panic_bounds_check`, as D11 accepts.
992//! * **No per-dereference `reinterpret_cast`.** `make_in_or_out_edge`
993//!   (`graph_adjacency.hh:328-341`) casts the CRTP base to the derived iterator on
994//!   every dereference just to read `_pos`. An anchored `Incident` needs neither.
995//! * **One `TypeId` compare at the boundary**, against up to three `any_cast`
996//!   probes per candidate plus a `try`/`catch` on the Python path.
997//! * **One `Vec` allocation per property map**, against `shared_ptr<vector<T>>`'s
998//!   two plus atomic refcount traffic on every copy into a parallel region.
999//!
1000//! ### Losses, stated
1001//!
1002//! * **No floating-point reassociation.** `#pragma omp parallel for reduction(+:S)`
1003//!   (`potts/spec.hh:133, :143`) *licenses* GCC to vectorise the accumulation.
1004//!   Rust's `f64 +=` does not, and measurement confirms it: a serial scan emits
1005//!   `addsd`, never `addpd`. **Five of the six source designs reported
1006//!   entropy-sum performance as parity-or-better without mentioning this.**
1007//!   `par::reduce::chunked_sum::<LANES>` restores instruction-level parallelism,
1008//!   and on the current toolchain the SLP vectoriser also packs the lanes --
1009//!   without any reassociation licence, because `LANES` independent accumulators
1010//!   fed from consecutive slots are a packed add *at the same association order*.
1011//!   Corrected from an earlier reading of this paragraph, which claimed a
1012//!   four-accumulator hand-unroll emits only `addsd`; it does not.
1013//!
1014//!   **The instruction mix, in two profiles, because it differs between them.**
1015//!   The numbers this paragraph used to carry -- "the scan is 9 `addsd` / 0
1016//!   `addpd`, and `chunked_sum::<4>` is 18 `addpd`" -- were taken with a
1017//!   standalone `rustc -O` probe, and they reproduce there exactly. They are not
1018//!   the shipped configuration. `benches/reduce.rs` carries `#[inline(never)]`
1019//!   probes so the same two forms can be disassembled out of `[profile.bench]`:
1020//!
1021//!   | form | `rustc -O`, standalone | `[profile.bench]` (opt-level 3, fat LTO, CGU 1) |
1022//!   |---|---|---|
1023//!   | serial `f64` fold | 37 insns, 9 `addsd`, **0 `addpd`** | 37 insns, 9 `addsd`, **0 `addpd`** |
1024//!   | `chunked_sum::<4>` | 117 insns, 13 `addsd`, **18 `addpd`** | 69 insns, 7 `addsd`, **6 `addpd`** |
1025//!   | `chunked_sum::<8>` | -- | 85 insns, 15 `addsd`, **4 `addpd`** |
1026//!
1027//!   The claim that matters is identical in both columns and is the one that is
1028//!   structurally guaranteed: the scan never packs, the lane form does. The
1029//!   `addpd` *count* is an unroll-factor artefact and should not have been stated
1030//!   as a constant. Every `addpd` here is SSE2, two lanes; the port ships
1031//!   baseline `x86-64`, so `-C target-cpu=native` would change these numbers
1032//!   again.
1033//!
1034//!   **What the licence is worth, which this paragraph never said.** 1 Mi `f64`
1035//!   (8 MB), `benches/reduce.rs::chunked_sum/lanes`:
1036//!
1037//!   | form | time | vs. the strict fold |
1038//!   |---|---:|---:|
1039//!   | serial `f64` fold | 1.247 ms | 1.00× |
1040//!   | `chunked_sum::<1>` | 1.246 ms | 1.00× (it *is* the fold) |
1041//!   | `chunked_sum::<2>` | 625.2 µs | 1.99× |
1042//!   | `chunked_sum::<4>` | 345.8 µs | **3.61×** |
1043//!   | `chunked_sum::<8>` | 333.6 µs | 3.74× |
1044//!
1045//!   So a strict left fold costs **3.6×** against this port's own deterministic
1046//!   lane form, and that is the size of the thing `reduction(+:S)` licenses.
1047//!   `chunked_sum` recovers essentially all of it at four lanes (3.61 of a 3.74
1048//!   ceiling). The reason it can is that the strict fold is latency-bound rather
1049//!   than bandwidth-bound: 1.19 ns per element is 6.72 GB/s, against the
1050//!   9.24-9.78 GB/s this same machine sustained on the flat adjacency scan two
1051//!   entries above, so the `addsd` dependency chain is the binding constraint
1052//!   and independent accumulators go straight at it. The loss that remains is
1053//!   the licence itself,
1054//!   at every site that still spells a reduction as `f64 +=`: graph-tool may
1055//!   reassociate a loop this port may not, so each such site pays up to 3.6×
1056//!   until it is converted. Explicit lane control still waits for `core::simd`.
1057//!
1058//!   The claim is no longer taken on trust:
1059//!   `tests/u11_reduce.rs::the_ledger_records_whether_chunked_sum_vectorises`
1060//!   disassembles both forms on every run, asserts only what is structurally
1061//!   guaranteed (a serial `f64` fold can never pack), and writes what it found
1062//!   to `target/debug/deps/u11_codegen_ledger.txt`.
1063//! * **Bounds checks on scatter.** `pm[target(e)] += x` keeps a compare per
1064//!   element that `unchecked_vector_property_map::operator[]` does not. Accepted
1065//!   per D11; `as_mut_slice()` is the escape for anything expressible as a scan.
1066//!
1067//! * **One allocation per SBM commit, which nothing else in the move cycle
1068//!   pays.** `Receipt` owns `entries: Vec<Entry<W>>` (`delta/lifecycle.rs:203`)
1069//!   so that the before-image survives into `audit_commit`, and building it is a
1070//!   fresh heap object on every move. Measured with a counting `GlobalAlloc`
1071//!   (`gt-inference/tests/ledger_sbm.rs`), over 10 000 moves after warm-up:
1072//!
1073//!   | stage | allocations per move |
1074//!   |---|---:|
1075//!   | `record` (`modify_entries` + `get_move_entries`) | **0** |
1076//!   | `sparse_ds` (`entries_dS`) | **0** |
1077//!   | `commit` | **1** |
1078//!   | `reseat` | **0** |
1079//!
1080//!   `DeltaBuf::begin` (`delta/buf.rs:149`) really does drain and clear rather
1081//!   than free, and the entry vector reaches its high-water mark and stays
1082//!   there -- the recorder allocated nothing at all across 10 000 moves once
1083//!   warm. The commit's one is structural, not an oversight: it is what D10's
1084//!   "the level is the unit of consumption" costs when the audit has to run
1085//!   after the state has already moved. It is a malloc/free pair against a
1086//!   1.97 µs move, so it is small; it is recorded because the surrounding
1087//!   design reads as though the cycle were allocation-free, and it is not.
1088//!   The whole cycle measures 1.97 µs per move at |V| = 20 000, |E| = 100 000,
1089//!   B = 64 (`benches/sbm.rs::sbm/move_vertex`), of which `record` is 1.31 µs.
1090//!
1091//! * **`add_edge` is O(1) amortised, but its constant grows with the graph.**
1092//!   Defect #18's detector (`benches/adjacency.rs::add_edge/scaling`) exists to
1093//!   catch a `Vec::insert` transliteration, which would double the per-edge time
1094//!   every rung. It does not double -- but it does not stay flat either, which
1095//!   the bench's own comment used to claim:
1096//!
1097//!   | edges (vertices = edges/4) | 10 k | 20 k | 40 k | 80 k | 160 k | 320 k |
1098//!   |---|---:|---:|---:|---:|---:|---:|
1099//!   | ns per edge | 53.8 | 57.0 | 80.0 | 89.8 | 107.9 | 187.1 |
1100//!
1101//!   3.5× over five doublings, against 32× for a quadratic insert and 1× for a
1102//!   flat append: the detector's purpose is intact and its stated acceptance
1103//!   criterion was wrong. The shape is what growing |V| independent `Vec`s under
1104//!   random access costs -- reallocation plus a cache miss per touched block --
1105//!   and the port has no way to avoid it today, because there is no
1106//!   `reserve_edges` on `AdjList` (the open item U6 recorded against D9: the
1107//!   builder can count degrees in parallel but cannot size the blocks, since
1108//!   `AdjList`'s fields are private to `adj/list.rs`). Sizing every block once
1109//!   is the fix and it is unwritten.
1110//! * **`swap_remove_vertex` is 2–4× slower.** C++ patches endpoints in place
1111//!   (`:1489-1523`); here it is unlink+relink per incident edge, which is the only
1112//!   way to make the stale-index class impossible rather than merely absent today.
1113//! * **`Filtered::new` costs an O(V + E) prepass.** C++ gets O(1) by returning the
1114//!   wrong number.
1115//! * **Fixed chunking loses to `schedule(runtime)`** on ragged workloads (§8).
1116//! * **Coarse recompilation.** Five crates against 277 TUs (§10).
1117//! * **Adjacency order changes after removals.** Swap-with-back against
1118//!   erase-and-shift (`:1257-1263`). `gt-io` therefore emits in `EdgeId` order,
1119//!   not adjacency order, so round-trips stay byte-reproducible.
1120//!

1144//! ## 13. Changes forced by the compiler
1145//!
1146//! Every item here is a signature that could not be written as designed.
1147//!
1148//! 1. **`Fill` with an associated context was dropped.** A blanket
1149//!    `impl<T: FillFree> Fill for T` overlaps a manual `impl Fill for PyValue`,
1150//!    and Rust cannot prove `PyValue: !FillFree`. Replaced by `Zeroed` (context-free,
1151//!    14 members) plus `sized_for_with(bound, fill: impl FnMut() -> T)` for the
1152//!    Python member. Strictly more general.
1153//! 2. **`InFields` with `unreachable!()` was replaced by `Field<D>`** and a
1154//!    `Vec<Vec<u32>>` field table of length `D::N_FIELDS`. No unreachable arm.
1155//! 3. **`Slots`/`Scan` removed as a type parameter** (D12); `EdgeSlots` is a
1156//!    field, and it carries endpoints.
1157//! 4. **`I: RawId` removed as a type parameter**; `ids::Raw` is a crate alias (D5).
1158//! 5. **`MaskFilter::new` removed.** Only `Filtered::masked` constructs one, so
1159//!    validation and use are one statement (§4).
1160//! 6. **`ExactIncidence`** carries its `ExactSizeIterator` requirement as a
1161//!    `where` clause on the trait declaration; as a supertrait bound on
1162//!    `GraphRef` it excludes filtered views.
1163//! 7. **`value_subset!` lives in gt-core**, with the types it names. Splitting
1164//!    macro and types across crates gives `error[E0433]` on every `$crate::` path.
1165//! 8. **`ParBuilder::fill(make: F)`** — `gen` is a reserved keyword in edition
1166//!    2024.
1167//! 9. **rand 0.9, not 0.8.** `rng.gen()` needs `r#gen` under edition 2024.
1168//! 10. **`[profile.bench] panic` removed** — cargo ignores it and warns.
1169//! 11. **`DynGraph`'s blanket impl needs a `GraphBaseExt` helper trait**, because
1170//!     `self.num_vertices()` inside it resolves to the trait method being defined
1171//!     and recurses.
1172//! 12. **gt-py carries `#![allow(unsafe_op_in_unsafe_fn)]` and a module-scoped
1173//!     `#![allow(clippy::useless_conversion)]`.** pyo3 0.22's macro expansion
1174//!     predates edition 2024. Both are removed when the workspace moves to a pyo3
1175//!     release built for it.
1176//! 13. **`PyValue` lives in gt-core behind `feature = "python"`**, not in gt-py,
1177//!     so that `PropValue`'s seal cannot be re-opened (§7).
1178//! 14. **`Scalar` excludes `long double`**; `LongDouble` is opaque (D7).
1179//! 15. **`ToF64` replaces `Into<f64>`** — no `From<i64> for f64` exists (D7).

1181//! 17. **`SlotRef` is 8 bytes**, not a packed `u32`. The `field:2 | other:30`
1182//!     packing caps the group count at 2³⁰ — a capability the C++ has — to save
1183//!     four bytes in a loop that runs once per cleared slot.
1184//! 18. **`AdjList` carries a reusable `Vec<EdgeId>` scratch**, rather than a
1185//!     per-call `Vec` or an inline small-vector that spills above degree 16.
1186//! 19. **`pair_mut` returns `Option<Pair<'_, T>>`** in caller order, with a `Same`
1187//!     variant (D9).

1255//! ## 15. What is still open
1256//!
1257//! 1. **The `GEN_DISPATCH` second layer** (§10, row 53). `all_types_func_wrap`
1258//!    indexes resolved types **by parameter name**; `PropValue::Elem` solves only
1259//!    the positional case. Likely a generated struct of associated types.
1260//! 2. **Heterogeneous coupled states.** `coupled_state_t` (`state.hh:110`) is a
1261//!    `std::variant` over pointers to *differently instantiated* states. A
1262//!    homogeneous `Vec<S>` covers the nested SBM only; layered/overlap/weighted
1263//!    need an enum (combinatorial) or `Box<dyn CoupledLevel>` (a virtual call per
1264//!    level per move — small against O(#entries) work, but not zero).
1265//! 3. **Whether a 32-bit count type is worth a second `Weight` impl.** `Entry<i64>`
1266//!    is 32 bytes; `Entry<i32>` would be 16, i.e. two per cache line in the
1267//!    `entries_op` loop.
1268//! 4. **Vectorising the reductions** (§12) once `core::simd` stabilises, and
1269//!    whether it can be done without reintroducing nondeterminism.
1270//! 5. **Property-map storage across FFI.** C++ hands `std::vector<T>&` to
1271//!    Boost.Python directly (`fast_vector_property_map.hh:224`). A numpy view over
1272//!    `DenseProp`'s `Vec<T>` reintroduces the aliasing `&mut` was protecting: a
1273//!    Python-side array view outliving a `sized_for` resize. This is where the
1274//!    remaining `unsafe` would accumulate and it needs a designed answer.
1275//! 6. **Whether `EHash` should ship at all**, or whether `find_edge`'s
1276//!    shorter-half scan is enough in practice. Shipping it doubles the
1277//!    `AdjList` monomorphisations reachable from generic kernels.
1278//! 7. **Measuring one fat module** (`graph_properties.cc`, ~1 090 leaves by the
1279//!    census) against its C++ translation unit, before the five-crate split is
1280//!    called final.

1284//! ## 16. Testing discipline this port requires
1285//!
1286//! Every source design said "verified by compiling it" and, in most cases, the
1287//! compiled artifact contained a defect the design's own claims denied. The
1288//! sharpest example: one crate's `ln_gamma` was stubbed to `x.ln()`, no test
1289//! asserted a number, and the pricing path was wrong on **194 of 269** moves —
1290//! because the `emat` was keyed on an unordered pair while lookup canonicalised to
1291//! `(min, max)`. It compiled, it passed its four tests, and it was 72% wrong.
1292//!
1293//! So: *it compiles* is not evidence. Required from the first implementation unit:
1294//!
1295//! * **proptest**, model-based, against a naive reference — for `AdjList`
1296//!   (add/remove/clear/swap\_remove sequences, `validate()` after every op, in-half
1297//!   cross-checked against the model) and for the SBM (random moves priced against
1298//!   a from-scratch entropy with a *real* `lgamma`).
1299//! * **trybuild** compile-fail fixtures pinning every negative guarantee in §14.
1300//!   The six verified in this document must become fixtures, or they will regress
1301//!   silently the first time someone adds a blanket impl.
1302//! * **criterion** from day one: the ledger in §12 has numbers in it, and numbers
1303//!   rot.
1304//! * **codegen assertions** on the hot loops: no `panic_bounds_check`, no
1305//!   `__rust_alloc`, in the disassembly of the named kernels.
1306//! * **differential testing against graph-tool itself**, on real graphs, with real
1307//!   numbers. Nothing in §14 is settled until the two implementations agree.
