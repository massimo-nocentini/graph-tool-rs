1//! # gt-py
2//!
3//! The Boost.Python replacement, and the only crate in the workspace that
4//! names `pyo3`.
5//!
6//! ## What the GIL guarantee actually is ([DESIGN](gt_core::design) D7, D9)
7//!
8//! `graph_properties_copy.cc:35-42` -- and its four verbatim clones at `:69`,
9//! `:104`, `:145`, and `graph_properties_copy.hh:36-40` -- computes
10//!
11//! ```text
12//! bool is_python = (tgt != typeid(object) || src != typeid(object));
13//! GILRelease gil(!is_python);
14//! bool parallel = (num_vertices(g) > thresh && !is_python);
15//! ```
16//!
17//! The connective is wrong and the sense is inverted. When **both** maps hold
18//! `python::object`, `is_python` is false, so the GIL is *released* and the
19//! loop *is* parallelised -- `Py_INCREF`/`Py_DECREF` across OpenMP threads
20//! with no GIL held, in exactly the case that needs it most. And the reason
21//! the author re-derived the predicate by hand at all is structural:
22//! `gt_dispatch_args::gil_release` (`dispatch.hh:152`) is a single
23//! compile-time constant per call site, while the value type is chosen by a
24//! *runtime* `typeid` probe, so one flag cannot say "release iff this leaf has
25//! no `python::object`".
26//!
27//! Three independent mechanisms replace it here, and the third is the one
28//! that actually holds:
29//!
30//! 1. Nobody writes the predicate: [`gil::copy_prop`]'s where-clause derives
31//!    it as a type-level lattice meet, resolved per monomorphised leaf.
32//! 2. The `Par` strategy's bounds (`S: Sync`, `T: Send`) are unsatisfiable for
33//!    the Python member, so even a *wrongly edited lattice* fails to compile.
34//! 3. [`PyValue`](gt_core::prop::PyValue) is `!Send` **by construction**. This
35//!    is the load-bearing one: a positive marker trait only guards the
36//!    functions that remember to require it, and `pyo3::Py<T>` is
37//!    unconditionally `Send + Sync`
38//!    (`pyo3-0.22.6/src/instance.rs:943-944`), so a sibling newtype that
39//!    forgets the marker otherwise sails straight into rayon.
40//!
41//! What Rust does **not** give for free, and the docs here do not claim:
42//! `Python::with_gil` inside a rayon closure compiles, because the token is
43//! acquired per worker and never crosses a thread boundary. The guarantee is
44//! that the *race* is inexpressible, not that the parallel loop is -- and the
45//! price is that a Python-valued property map is serialised, which is the
46//! correct behaviour and what the C++ intended before the predicate was
47//! inverted.
